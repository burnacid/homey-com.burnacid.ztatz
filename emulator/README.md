# ZTATZ API emulator

A stand-in for a real ZTATZ / P1 Monitor, used to develop and test the Homey app without a P1 Monitor.

- It emulates all 100 routes of the ZTATZ 4.2.0 API (`/api/v1/...` and `/api/v2/...`).
- A built-in simulator keeps the data live and realistic.
- Scenario switches let you trigger edge cases.
- No npm dependencies. It needs Node.js 22.16 or newer for `node:sqlite` (tested on Node 26).

```sh
npm run emulator                     # or: node emulator/server.js
node emulator/server.js --port 8080 --speed 60 --history-days 400 --quiet
```

| Option | Default | |
|---|---|---|
| `--port` | `8080` (or `$PORT`) | HTTP port |
| `--host` | `0.0.0.0` | bind address. Keep this so a Homey on your LAN can connect |
| `--speed` | `1` | simulated seconds per real second |
| `--history-days` | `400` | days of history generated at startup (takes about 1.5 s) |
| `--quiet` | off | don't log every request |

On startup the emulator prints its LAN address, for example `http://192.168.1.10:8080`. Use that address as the URL when you pair a device in the Homey app.

## Control page

Open `http://<pc-ip>:8080/emulator`. It shows live values, every scenario switch, time controls, and an API explorer.

The same switches are available as JSON:

```sh
curl http://localhost:8080/emulator/api/state
curl -X POST localhost:8080/emulator/api/scenario -H 'Content-Type: application/json' \
     -d '{"availability":"offline"}'
curl -X POST localhost:8080/emulator/api/action -H 'Content-Type: application/json' \
     -d '{"action":"jump","time":"23:59:30"}'
```

| Scenario key | Values | Effect |
|---|---|---|
| `availability` | `ok`, `offline`, `html`, `error500`, `slow` | `offline` drops the TCP connection. `html` returns an nginx `502` HTML page. `error500` returns a falcon 500. `slow` waits `slowSeconds` before answering |
| `slowSeconds` | 0–300 | delay in `slow` mode |
| `emptyData` | bool | every data route returns `[]` |
| `phases` | `1`, `3` | single- or three-phase meter. In single-phase mode L2/L3 report 0 V / 0 A |
| `phaseLabels` | `current`, `legacy_v241` | `legacy_v241` uses the ZTATZ 2.4.1 status labels `Huidige Amperage L2 (71.7.0)` and `Huidige Voltage L2 (72.7.0)` for L3 |
| `water` | `none`, `pulse`, `digital`, `both` | `pulse` = TIMEPERIOD 11–15 (`/api/v2/watermeter/*`, `/watermeterdigital/*/1`). `digital` = P1 telegram meter, TIMEPERIOD 21–25 (`/watermeterdigital/*/2`) |
| `gas`, `heating`, `s0Production`, `solarEdge` | bool | turn individual meters on or off |
| `power` | `{mode: auto\|manual, consumptionW, productionW}` | `manual` forces fixed values. Set production above consumption to simulate exporting |
| `tariff` | `auto`, `P`, `D` | `auto` = P on weekdays 07–23, D otherwise |
| `newVersion` | bool | fills the "Laatste P1 monitor versie …" status rows and sets status 136 to `1` |
| `speed` | 0–3600 | time multiplier |

Turning a meter **off** deletes its rows, so the API returns `[]`. Turning it back on records new data from that moment on. Use *Reset* (`{"action":"reset"}`) to regenerate the full history.

Actions:
- `jump` — fast-forwards to the next `HH:MM[:SS]`, with no gaps in the data. Useful for testing midnight resets.
- `advance` — moves forward `{minutes}`.
- `pause` / `resume`
- `reset`

## How faithful is it?

The emulator is built directly from the exported ZTATZ source in `../ztatz/scripts`:

- `data/*.json` is generated by `tools/extract.py`. It contains:
  - the literal `CREATE TABLE` statements;
  - the default `config` and `status` rows;
  - every `HELP_*` text;
  - the SQL base strings of each API class;
  - the catalog route list.
- Each route builds its SQL exactly like the Python code, runs it on an in-memory SQLite database, and formats the result like Python's `json.dumps`. That covers:
  - `", "` separators, `12.0` floats, sorted keys in `json=object` mode, and `TIMESTAMP_lOCAL`.
  - Errors are always HTTP 500. They come back as **YAML** unless the client prefers JSON (send `Accept: application/json`). Unknown routes return 404 `title: 404 Not Found`.
  - Parameter quirks are reproduced: `limit=+5`, `range` vs `starttime` (the last one wins), lenient vs strict timestamps.
  - Bugs in the original are reproduced on purpose: `phaseminmax` with `round=on`, `starttime` or `range` fails with a DB error; `watermeterdigital/*/6` is unreachable.
- There are no `/api/v1/watermeter/*` routes. They return 404, like real ZTATZ 4.x.

`tools/parity.py` checks this against the real code:
- It takes a snapshot of the emulator database and loads the real `P1Api.py` (falcon) on top of it.
- It then compares about 1,200 requests (every route × parameter combinations × Accept headers) byte for byte.

```sh
python -m venv .venv && .venv/Scripts/pip install falcon pyyaml pytz psutil pycryptodome cryptography pynacl
node emulator/server.js --port 8080            # terminal 1
.venv/Scripts/python emulator/tools/parity.py  # terminal 2  ->  "... 0 mismatches"
```

With `phaseLabels: legacy_v241`, the status rows 102/105 show up as mismatches. That's expected: the real `rtStatusDb.init()` renames those labels when it opens the snapshot.

The routes whose output depends on the system are simulated: `datetime` (internet time equals the simulated time), `wifi/ssid` (fixed SSIDs), and `p1port/telegram` (a DSMR 5 telegram with a valid CRC, built from the live state). The catalog uses this PC's LAN IP as its prefix.

## Simulation

| Every | Writes |
|---|---|
| 10 s | `e_serial`, `faseinformatie`, `temperatuur` (10) and the live status rows (power per phase, V, A, tariff, daily max/min, …) |
| minute | `e_history_min` plus hour/day/month/year rollups (deltas, gas per P1Db rules), `watermeter`, `powerproduction` (S0, 2000 pulses/kWh), `temperatuur` 11–15, `faseminmax_dag`, `e_financieel_*` (tariffs from config) |
| 15 min | `powerproduction_solar` (SolarEdge interval values, TIMEPERIOD 21–25) |
| 10 min | `weer`, `weer_history_*` |
| hour | `energieprijzen_uur` (today, and tomorrow after 13:00), `statistics`, retention cleanup |

The house model includes:
- base load with appliance events spread over the phases (kettle, washing machine, EV charger, …);
- a seasonal solar curve on L1;
- heating gas use driven by outdoor temperature, plus showers;
- water usage;
- central heating supply and return temperatures;
- weather;
- dynamic prices.

It works out to about 3,400 kWh, 1,500 m³ gas and 3,600 kWh of solar per year.

To regenerate `data/` after updating the ZTATZ export:

```sh
python emulator/tools/extract.py
```
